# Improve run, 2026-10-20

Branch `improve/auto-2026-10-19`, from `main` at `53f7f3e` (2.0.0). Ten
read-only analysis agents (security, correctness, tests, docs, UI in a
browser, design, refactor, performance, a11y, config), then triage: high and
medium fixed, low left alone on purpose. Both test suites (Odoo 19 and 20)
were green before and after each iteration.

## Iteration 1

**Chat window**
- The bus payload now carries `channel_id`, so Stop shows while a run is
  live (`runtime/stream.py`, `static/src/chat/run_events.js`).
- A reload no longer loses a waiting approval: the thread asks
  `pan_ai_state` when an AI channel opens and rebuilds the card and Stop
  (`static/src/chat/thread_patch.js`, `run_events.hydrate`).
- Switch agent opens: the picker is a static import (Odoo's bundler has no
  dynamic import) (`static/src/chat/thread_actions.js`).
- Odoo's channel actions that mean nothing in a one-person agent chat
  (invite, favourites, mute, recordings, hide, pin, rename, leave) are
  hidden on `ai` channels.
- Action icons carry a Font Awesome name for Odoo 19 (`compat.actionIcon`).
- Stop on a waiting approval, or the stuck cron, writes the final body and
  tells the window (`stream.finish_outside`), so no card or "Thinking" stays.
- a11y: the stream is `aria-live`, the approval group and buttons are
  labelled, the error is `role="alert"`. The approval card's border is
  amber (a status), not the accent (`docs/brand.md` updated).

**Runtime**
- Stop between a tool call and its result, or on a waiting approval, closes
  the open calls with "Stopped by the user." so the next message works
  (`slices.close_open_calls`, `thread._close_open_calls`).
- The heartbeat beats on a clock (every 10 s) while the model is silent;
  a claim goes stale after 45 s, not 30 (90 s since iteration 2:
  `slices.beat`, `run.STALE_SECONDS`).
- A tool that fails at the database (foreign key, missing value) runs in a
  savepoint and returns the error to the model instead of aborting the run.
- The agent's `time_limit` is enforced in the slice loop, on the time
  worked in slices (`worked_seconds`), not on the clock: waiting in the
  queue or for an approval does not count.
- A thread keeps its last 60 messages, cut at a user prompt; a continuous
  thread that hits a limit pauses instead of failing every tick.
- The cron budget accounts for the slice it starts; `limit_time_real_cron`
  -1 means `limit_time_real` (Odoo's rule) and 0 means the default of
  120 s, not 10 s (`slices.server_limit`).
- The hourly cap refuses what a person starts by hand (a chat, a Fill
  button) and counts their chats and triggered runs; a watch's ticks, a
  schedule and the nightly fills are the administrator's settings and are
  never refused. A tick creates its run and leaves it to the budgeted
  worker loop; it moves its cursor only after the run started.
- The claim fence compares Python UTC timestamps, not the database's
  session-time `now()`.
- `_after` survives a record that refuses the note or the activity; the run
  says so in `error`.
- Triggered runs (an automation in somebody's request) go to the worker
  crons whole; the person's transaction is theirs. Scheduled runs are
  unchanged.
- `pan_ai.run.error_code` (limit, model, timeout, build, access, unresolved,
  stuck, other); the heartbeat counts those, never the error text.

**AI fields**
- `pan_ai_fill` is guarded: internal users only, write access on the
  records, at most 50 at once, the agent's own checks.
- Fill now queues the cron (`pan_ai.fill_now`), one batch per wake, instead
  of up to 200 model calls in the button's request.
- A record the run user may not write, or that failed, is recorded and left
  alone for a day, so a batch rotates through the table.
- `pan_ai_fields_of` is an ormcache per model, cleared when a prompt changes
  (every write on every model asks it).
- The Enterprise seam's write of the prompt is explicitly sudo.

**Platform client**
- The platform URL override must be https (http on this machine only) and
  is logged on every use; redirects are never followed.
- One refusal message per state (pending, revoked, refused, no plan, lapsed).

**Defaults, settings, docs, CI**
- `defaults.py` holds the four defaults Settings and the code shared.
- Settings: titles back on the four inputs, Remove key in the Danger zone,
  "Delete all threads". Runs: duration in seconds, a display name.
- The default agent is "Odoo agent" on a fresh install; an upgraded
  install keeps the name it has (the record is `noupdate`).
- `ARCHITECTURE.md` points at `docs/architecture-20.md`; the architecture,
  plan, protocol and execution plan say what shipped (plain key by decision
  16, one live run per thread, error codes, no code execution).
- CI runs on branches with a slash; `no_em_dash.py` scans views, data and
  the chat bundle; `cryptography>=45` pinned beside pyOpenSSL.

**Left alone (low, or needs a human)**
- Low findings of every agent (about 50).
- `static/description/banner.png` is a placeholder: the banner is a brand
  asset to render in the brand repo.
- A Discuss sidebar category for AI chats: a design choice; "Open in
  Discuss" still lands with an empty sidebar.
- OpenRouter key and MCP tokens stay plain (decision 16); the docs now say
  so instead of promising encryption.
- The Enterprise 20 seam is still unmeasured on a real Enterprise.

## Iteration 2

Analysis again for the domains with open findings (correctness, refactor,
performance, tests, design, UI), then the fixes.

**Bugs**
- `pan_ai_state` (what the window asks on open) answered any internal user
  who knew a channel id; now the chat's owner only.
- A tool longer than the stale window lost its claim and the round ran
  twice: every Odoo tool beats the heartbeat before and after its work,
  and the window is 90 s.
- A worker that lost its claim could still write a failure over the live
  worker's run: `_fail` checks the fence first.
- A reclaimed slice appended the model's answer to a dead worker's half:
  the run's text is written at slice boundaries and at the end only, no
  longer ten times a second.
- Two starts on one thread (a double send, both worker crons on one due
  tick) could both pass the live-run check: a partial unique index on
  `pan_ai.run` refuses the second with the same message; an upgrade first
  fails the older of any two live runs a database already holds.
- A server action's `fields` parameter was renamed to `fields_` like a
  built-in's.

**Performance**
- The nightly AI-fields cron has a deadline inside the cron's limit and
  re-arms itself for what is left (a cursor, so every field gets one batch
  a night and none is starved), instead of being killed and, after a few
  nights, switched off by Odoo. A field fill never searches the web.
- `live_run_id` is one bounded query; retention also drops the finished
  runs of watches and rules and the threads of old field fills.
- The field state rows are written in two statements, not one per record.
- The worker loop gives every claimable run one slice per pass.
- The tool log is bounded by shape (last 200 calls, args clipped), so it
  stays JSON.

**Simpler**
- `Run._run_now(where)` is the one place a claim and a slice are spelled.
- `fill()` builds its agent through `build_agent` (output, prefix, tools
  as overrides) and has one failure helper.
- The slice loop dispatches to three small helpers per node kind.
- Dead fallbacks on `time_limit`, a second parse of the conversation and
  the second clause of the OdooBot check are gone.

**Copy**
- Settings: a saved key says "Saved"; Delete all threads says the runs go
  with them (they do; the old copy promised otherwise); one-sentence
  help lines; the Danger zone says each consequence in the confirmation.
- Refusals name the limit ("hourly limit") and say what to do; errors in
  the chat point at the server log instead of a Python class name.
- Thread form: kind as a field, Resume not primary, paused once; the cron
  is "fill AI fields"; one name for the Fill button.

**UI** (checked in a browser, desktop and phone)
- The continuous thread form rendered an error dialog: the domain widget
  wanted a model name, not a row.
- Ctrl+K "Ask AI" failed on Odoo 20 (the palette calls a provider without
  `env` there).
- The server action "Run AI agent" fields had no labels; they sit in a
  group of their own now.
- A chat thread is named after its first prompt, so the Threads list is
  readable; the Paused column is optional; the Runs tab opens a run; a
  plain user cannot create a thread by hand; the approval buttons show
  their focus.

**Tests** (79 on each version): access per group on both versions, the
window state's ownership and content, the markdown sanitizer, every
failure code, the watch's edge paths and its pause on a limit, a server
action as a tool, a record that refuses the note, the history trim through
a real slice, the bounded tool log, retention of the other kinds, the
unique live run, the config-parameter shim and the bus.

## Iteration 3

Analysis again for security, correctness, docs and the UI, then the fixes.

**Security**
- The Settings buttons (Remove key, Delete all threads, Connect, Check,
  Disconnect) are public methods any session could call by name; each now
  asks for the Settings administrator.
- A person had write access to their own thread rows, including the
  conversation and the pending calls, so an approved call could be forged
  with other arguments and run as the agent's dedicated user. The user's
  row is read-only now; the runtime writes threads (sudo), Pause and
  Resume check the owner and write through sudo, and a plain user cannot
  create a continuous thread by RPC any more.
- The Action menu starts at most 50 runs at once and counts against the
  person's hourly cap; a rule's runs still never refuse a save.
- The Enterprise seam writes the prompt as the person who clicked (an
  administrator), and its fill counts as by hand when a request is behind
  it (Odoo's own nightly cron reaches the seam too; not yet measured on
  a real Enterprise 20).
- `pan_ai_open` checks read access on the channel it is asked about.

**Bugs**
- The agent's request and token limits reset on every slice; each slice
  now starts from what the run spent, so they hold per run, and a slice
  that fails still books its spend.
- Both worker crons on one due tick: the loser paused the watch. A live
  run is a distinct refusal (`StillAnswering`) that the tick skips.
- A many2one id the model invented failed at commit, outside the try,
  and aborted the whole fill wake. The write runs in a flushing
  savepoint, a value that does not fit is the record's failure, an
  unknown id and an empty answer count as unresolved (a boolean false is
  an answer).
- A field-fill run was claimable by the worker crons while the fill ran
  it: it is claimed from birth by the worker "fill", which the slice loop
  never takes (the stuck cron still fails a dead one).
- The fill cron's deadline leaves room for the model call it starts.
- A tool's after-beat committed a dead worker's writes: the beat is
  behind the claim fence and a lost claim rolls back.
- A tick that found more than 50 changes lost the older ones; the cursor
  is a pair (the last change named and its id, since one transaction
  stamps every record it touches with the same write_date) and the rest
  comes next time. A new watch starts from now instead of walking the
  model's history.
- The stuck cron failed healthy runs on wall-clock age; it looks at the
  last sign of life (heartbeat, or the start) and leaves waiting runs be.
- Stop between a tool round and the next model call replaced the round's
  real returns with "Stopped by the user."; the round's returns stay.

**UI**
- A run that ended while the page was loading no longer flashes raw
  markdown over its rendered body.
- The run form shows the answer rendered and is read-only; the thread's
  bookkeeping is read-only; the watch group has plain labels.

**Docs**: the execution plan's security checklist and the architecture
say what the code does (per-run limits, Allow and Skip on the same run,
the bus event names, where scheduled and triggered answers land, who may
configure, the heartbeat, the fill cron, auto update nightly). The unused
`access` error code is gone.

**Tests** (86 on each version): the Settings buttons refuse a user, a
person never writes their thread, the Action menu is by hand and bounded,
a full tick keeps its place, a waiting run with a recent heartbeat is not
stuck, the request limit holds across slices, an empty or invented value
is unresolved, Stop keeps the round's returns.
